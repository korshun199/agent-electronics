# Полётный контроллер по USB: проверка перед UART-тестом

Дата наблюдения: 2026-11-12.

## Что видно из среды Codex

- USB-устройство перечислено как `Betaflight STM32F7x2`, VID:PID `0483:5740`.
- Ядро связывает USB-интерфейс с `ttyACM0` в sysfs, то есть устройство объявляет CDC serial-интерфейс.
- Само устройство видно в sysfs, но `/dev/ttyACM0` и `/dev/bus/usb` в текущей среде Codex не доступны. `lsusb` также не смог открыть libusb (`-99`). Поэтому здесь нельзя прочитать CLI/конфигурацию контроллера или обращаться к его USB-интерфейсу.
- Файл `/home/work/firmware/RAsBERY_DRON.txt` — текстовый экспорт конфигурации Betaflight, не бинарный дамп Flash и не исходный код.
- В заголовке файла указаны Betaflight 4.5.1, target `BEASTFPVF722`, manufacturer id `BSTF`, MSP API 1.46. Это точнее USB-строки `STM32F7x2`, но не заменяет схему платы и не подтверждает назначение её разъёмов.
- Официальная карта target Betaflight подтверждает MCU семейства `STM32F722` и назначает UART5 на выводы микроконтроллера PC12 (TX) и PD2 (RX). Это не устанавливает, к каким именно площадкам/разъёму платы подведены эти выводы. На момент первоначальной проверки полного бинарного чтения ещё не было; позже владелец предоставил файл `/home/work/tmp/RASPBERRY_DRON.bin`.
- Страница производителя для target `BEASTFPVF722` указывает точную модель MCU `STM32F722RET6`; документация ST указывает 512 Кбайт пользовательской Flash. Полный диапазон для чтения: `0x08000000` + `0x80000` байт. Подготовлена отдельная процедура чтения через встроенный USB DFU: [FC_FLASH_DUMP_PROCEDURE.md](FC_FLASH_DUMP_PROCEDURE.md).
- Повторная read-only проверка среды: USB CDC FC виден в sysfs, но `lsusb`/`dfu-util` не могут открыть libusb (`-99` / `LIBUSB_ERROR_OTHER`); `/dev/bus/usb` и `/dev/ttyACM*` отсутствуют. `st-info --probe` обнаружил 0 ST-Link. Поэтому физически прочитать MCU из этой среды нельзя; предоставленный бинарный файл проверен отдельно ниже.
- SHA-256 текстового экспорта: `3528c9e0144b9f7f3d317bc944d5cebae8a0e372f96ebd398e9e61344bcdf9c1`.
- Read-only поиск по локальным `.bin`, `.hex`, `.dfu`, `.elf` и `.uf2` в `/home/work/firmware` не нашёл маркеров `BEASTFPVF722`, `BSTF`, `STM32F7X2` или версии `4.5.1`. Например, `/home/work/firmware/BTF.bin` содержит строки `STM32F405` и `4.5.2`; это другой target и другой контроллер. Такие образы не использовать для этого F722.

Текстовый экспорт и USB-описание согласуются. Однако сам конфиг не прочитывался с USB в этой среде, фактическое состояние контроллера в момент проверки и физические соединения не измерялись. Запись в контроллер не выполнялась.

## Полученный бинарный файл FC

Проверен файл `/home/work/tmp/RASPBERRY_DRON.bin` только чтением:

- Размер: `524288` байт (ровно 512 КиБ), совпадает с объёмом Flash STM32F722RET6.
- SHA-256: `37fd659bd21d285c75fc8c6570ae566de0cb55122426967b45911d0f5cd702ed`.
- `file` распознаёт ARM Cortex-M образ; начальный SP `0x20010000`, reset vector `0x08056241`. Адрес обработчика попадает в диапазон Flash `0x08000000..0x0807FFFF`.
- Статическая Thumb-дизассемблировка reset-обработчика по адресу `0x08056240` показывает последовательность стартовой инициализации перед переходом в основное приложение; бинарник не запускался.
- Внутри есть строки `BEASTFPVF722`, `Betaflight`, `BETAFLIGHT`, `STM32F7x2` и `4.5.1`. Это сильное совпадение с target и версией текстового CLI-экспорта.
- Область смещения `0x70000..0x7FFFF` (адреса `0x08070000..0x0807FFFF`) целиком заполнена `0xFF`; это похоже на неиспользованную часть Flash и не означает само по себе, что чтение оборвалось.
- В смещении `0x4000` обнаружена сохранённая EEPROM-конфигурация Betaflight: 81 запись, корректная структура и CRC-16/CCITT `0x1D0F`; последняя запись заканчивается в `0x4FEC`, остаток до `0x8000` стёрт. Это независимо подтверждает, что в дампе есть область сохранённых настроек.
- Файл не запускался, прошивка/Flash/option bytes не менялись.

Размер и внутреннее содержимое согласуются с полным чтением основной Flash нужного FC. Файл не содержит лога STM32CubeProgrammer, поэтому адрес чтения и связь полученного файла с конкретным подключением нельзя независимо подтвердить только по бинарнику. Подробная запись: [FC_FLASH_DUMP_PROCEDURE.md](FC_FLASH_DUMP_PROCEDURE.md).

## Найденная UART-конфигурация

В Betaflight 4.5.1 команда `serial` использует старый числовой формат идентификатора порта и маски функций. По таблице официальной документации Betaflight в строках этого файла:

- `serial 20 1 115200 ...` — USB VCP, функция MSP на 115200 бод.
- `serial 0 64 115200 ...` — UART1 назначен Serial RX; конфигурация также указывает `serialrx_provider = CRSF`.
- `serial 3 8192 ...` — UART4 назначен VTX Tramp.
- `serial 4 1 500000 ...` — UART5 назначен MSP на 500000 бод.
- UART2, UART3 и UART6 имеют маску функций `0` в данном экспорте.
- На уровне MCU target Betaflight сопоставляет UART5 с PC12 (TX) и PD2 (RX); физическую маркировку разъёма по этой карте определить нельзя.

Эти настройки проверены ещё и в самом бинарном дампе: запись `PG_SERIAL_CONFIG` (PGN 13, версия 1) имеет 112 байт данных. Её стандартные записи для USB VCP и UART1–UART6 совпадают с перечисленными строками CLI, в частности UART5 сохранён с функцией MSP и индексом скорости 10, который в Betaflight 4.5.1 означает 500000 бод. Значит, экспортированный текст соответствует конфигурации, сохранённой во Flash на момент получения дампа. Это не подтверждает физическое соединение UART5 с Raspberry Pi.

`feature TELEMETRY` включён, но строка UART5 назначает именно MSP, не отдельный телеметрический протокол. Это важно: Pi-приложению, если оно подключено к этому порту, нужно понимать MSP; само совпадение слова «UART5» не доказывает, что кабель действительно соединяет эти два порта.

Внутри `boot.img` Raspberry Pi также найдены `dtoverlay=uart0` и `dtoverlay=uart5`. Это делает связь Pi с полётником по дополнительному UART5 правдоподобной гипотезой. Подтверждений фактической разводки, устройства Linux, скорости Pi-приложения и направления обмена пока нет. Контрольный QEMU-запуск с тестовым `Serial` дошёл до передачи через backend UART0; на штатной виртуальной конфигурации выполнение останавливалось раньше. Это ничего не устанавливает о порте позднего приложения.

Рабочая гипотеза о двух независимых каналах остаётся возможной: ранний `get-key` передаёт двоичный запрос через UART0 в синтетическом QEMU, а пользовательское приложение могло использовать отдельный Pi UART5 для MSP к FC UART5 на 500000 бод. Наличие обоих overlays и настройки FC согласуется с этой схемой, но не доказывает её: root приложения Pi зашифрован, физическая трассировка GPIO/HAT до FC не подтверждена. Сохранённый захват сделан одноканальным USB-UART-приёмником; неизвестно, какая именно TX-линия была подключена.

## Что означает идея временной прошивки

Тестовая прошивка, собранная в STM32Cube, технически возможна лишь как отдельная программа под точный MCU и плату. Данный текстовый конфиг не является исходным кодом Betaflight и не превращается в Cube-проект. Замена прошивки выведет штатные функции полётника из работы до восстановления совместимой Betaflight-прошивки.

Сначала разумнее проверить существующий MSP на UART5 @ 500000: он уже задан в экспортированной конфигурации. При необходимости штатный UART меняют через Betaflight Configurator, но это тоже запись настроек во внешнее устройство. Ни конфигуратор, ни CLI из среды Codex сейчас недоступны; никаких настроек не меняли.

Сохранённый Raspberry Pi UART-захват и `get-key` относятся к исследованному обмену на этапе загрузки/разблокировки. Они пока не показывают запросы и ответы MSP работающего приложения Pi.

## Безопасный порядок дальнейшей проверки

1. По уже имеющемуся экспорту изучить код/настройки Raspberry Pi, если они доступны; основной проверяемый кандидат — MSP на UART5, 500000 бод.
2. Подтвердить физические точки Pi UART5 и FC UART5 по документации конкретных плат перед любым подключением логгера.
3. Перед будущими экспериментами с прошивкой сохранить исходный файл `/home/work/tmp/RASPBERRY_DRON.bin` отдельно и сверить его SHA-256 с записью выше. Образ по размеру и содержимому согласуется с полным дампом `STM32F722RET6`; лог операции чтения отсутствует. Cube-прошивку не выбирать по одному лишь семейству `STM32F7X2`.
4. До любого теста с двигателями снять пропеллеры и отключить силовое питание ESC/моторов. Любая запись прошивки требует отдельного явного согласования, проверенного резервного образа и проверки записи.
